Background & Problem Context

Modern organisations will increasingly rely on CI/CD pipelines and cloud-native delivery mechanisms for rapid software deployment.

  • Security scanners (Semgrep, Bandit, Trivy, Checkov, Gitleaks, OSV-Scanner) routinely emit findings in standard formats (SARIF).
  • However, these tools STOP at detection.
  • Currently, there is no reliable system for prioritisation, patch generation, pull request creation, or post-fix validation.
  • The integration of Large Language Models (LLMs), Retrieval-Augmented Generation (RAG), and agentic workflows will create an unprecedented opportunity to close this gap.

Key Statistic: Vulnerability remediation will remain slow, fragmented, and heavily manual, creating significant windows of exposure.

Statement of the Problem

The Remediation Bottleneck

  • Automated scanners will continue to be widely used, but remediation will remain a manual bottleneck.
  • Development teams will receive more findings than they can triage, leading to:
    • Increased Mean Time To Remediate (MTTR)
    • Developer alert fatigue
    • Unresolved exploitable vulnerabilities

Limitations of Existing Tools

  • Constrained by platform lock-in and single-scanner scope.
  • Provide weak contextual awareness and limited LLM provider choice.
  • Lack post-deployment validation of applied patches.

Core Problem: The study will address the absence of a vendor-neutral, policy-controlled, multi-scanner, LLM-assisted remediation system, which is especially critical for Nigerian/African SMEs with limited security headcount.

Aim & Research Objectives

AIM: The study will design, implement, and evaluate InfraGuard Pro — an LLM-based autonomous security remediation system that will consume heterogeneous CI/CD scanner findings, generate policy-controlled patch proposals, and validate outcomes through closed-loop observability.

O1

Objective 1: Requirements

The system will gather and analyse functional, non-functional, security, operational, and user requirements.

O2

Objective 2: Design

The study will design the architecture, data flow, database model, policy model, and interaction workflow.

O3

Objective 3: Implementation

The study will develop the system using SARIF ingestion, RAG-based evidence retrieval, LLM provider abstraction, policy-controlled patch generation, Git PR integration, and audit logging.

O4

Objective 4: Evaluation

The study will evaluate effectiveness, safety, performance, cost, and usability against real-world and synthetic findings.

Research Questions

The proposed research will answer the following key questions:

  1. What functional and non-functional requirements will be necessary for a safe LLM-based autonomous security remediation system in cloud-native CI/CD environments?
  2. How can a vendor-neutral architecture be designed to ingest heterogeneous SARIF findings, retrieve evidence, generate patch proposals, and route actions through policy controls?
  3. How can InfraGuard Pro be implemented using appropriate programming languages, frameworks, databases, LLM providers, observability tools, and CI/CD integrations?
  4. To what extent will the developed system improve remediation effectiveness, reduce MTTR, control LLM cost, prevent regressions, and support operator trust vs. manual triage?

Literature Gap & Theoretical Framework

Identified Gaps

  • Most solutions will not orchestrate findings across multiple scanner categories through a single SARIF-based pipeline.
  • Many will remain tied to one LLM provider, scanner vendor, or repository platform.
  • Few will clearly distinguish recommend-only, human-approved, and autonomous-low-risk modes.
  • LLM-generated patches will rarely be validated through both scanner re-runs AND telemetry.
  • Limited published evidence will exist on cost, latency, accuracy, regression rate, and operator trust for autonomous remediation in resource-constrained environments.

Theoretical Frameworks

Methodology

Hybrid Agile-DevSecOps + Design Science Research

1. Requirements

Literature review, DevSecOps workflow analysis, scanner output inspection, and MoSCoW prioritisation will produce a requirements catalogue.

2. Design

Architecture-driven, OO modelling will map architecture, use-case, sequence, ER, data-flow, and policy models.

3. Implementation & Testing

Iterative sprints will be executed using FastAPI, LangGraph, ChromaDB, and Docker. Testing will include Unit, Integration, API, Security, Scanner re-runs, and UAT.

4. Evaluation

The system will benchmark against real-world and synthetic findings, measuring patch acceptance, MTTR, regression rate, and LLM cost.

Scope & Delimitation

Within Scope

  • SARIF v2.1.0 ingestion from 6 targeted scanners (Semgrep, Bandit, Trivy, Checkov, Gitleaks, OSV-Scanner).
  • RAG-based retrieval from advisories, runbooks, and historical outcomes.
  • LLM provider abstraction for managed and self-hosted endpoints.
  • Policy routing modes (recommend, human-approval, autonomous).
  • Pull-request creation via Git APIs + closed-loop validation.

Intentionally Excluded

  • Fine-tuning or training a new LLM from scratch.
  • Formal commercial certification (SOC 2, ISO 27001).
  • Full mobile or native desktop client.
  • Network intrusion prevention beyond available integrations.
