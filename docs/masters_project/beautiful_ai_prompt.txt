2. The operational problem - "Telemetry exists, but first-pass interpretation remains manual"
   Frame the project around small operations teams comparing distributed signals before deciding
   whether a service is healthy, degraded, or failing.
   - Triage time. When several telemetry sources report a problem, a responder must compare the evidence before stating the likely cause and next action. This work tests whether a bounded first-pass summary can support that review.
   - Repeated low-risk findings. A known condition may appear on successive heartbeat cycles and occupy the same dashboard space as an unreviewed finding.
   - Ungrounded model output. An LLM can infer a cause that is not supported by the supplied telemetry or treat an optional integration as a fault. Its response therefore needs scope constraints, structured parsing, and operator review.
   - Deployment and data handling. Managed platforms and cloud model APIs differ in cost, hosting model, and the telemetry they receive. A small team needs a design whose data boundary can be inspected and configured.
   - Limited operator memory. A recurring condition may appear on every heartbeat even after an operator has reviewed it. Without an acknowledgement mechanism, the dashboard provides no durable way to distinguish a known low-risk condition from an unreviewed one.
   Closing line: Five practical issues remain even when monitoring tools are already in place: The project therefore asks how a bounded, self-hosted triage system can turn available telemetry into a reviewable verdict, retrieve relevant runbooks, support operator-approved threat response, and remember recurring conditions without concealing high-risk findings.

3. Aim and objectives - "Five objectives connect telemetry collection to verified behaviour"
   Aim: The aim of this research is to design, develop, and evaluate InfraGuard AI, an LLM-assisted observability and incident-triage system that produces structured verdicts from available telemetry, supports operator-approved threat response and runbook retrieval, and records acknowledgements for recurring low-risk conditions.
   - To design and implement a multi-source telemetry-collection layer that uniformly gathers application and system logs (via Grafana Loki), infrastructure metrics (via Prometheus), endpoint health (via HTTP probes), and optional container state (via the Docker Engine API), and normalises them into a bounded context suitable for downstream LLM reasoning.
   - To develop a LangGraph reasoning workflow following a collect, analyse, decide, and notify cycle that requests a structured JSON verdict from a configured LLM provider and sends notifications for high and critical verdicts.
   - To design and implement a retrieval-augmented runbook assistant that indexes local Markdown procedures with local ONNX embeddings and ChromaDB, then supplies relevant excerpts to the selected language model.
   - To implement an acknowledgement memory keyed by a fingerprint of the condition signature, prompt version, and model, so matching low-risk verdicts can be marked and hidden by default while high and critical verdicts remain visible.
   - To package the system for single-host deployment through Docker Compose and evaluate the implemented behaviour through automated tests and measured code coverage. A practitioner usability protocol is also defined for later administration.
   Show the objectives as a clean numbered progression, not five dense text boxes.

7. Architecture - "A two-process, single-host design keeps collection and review inspectable"
   Core architecture: InfraGuard AI runs as two processes. The agent process executes the reasoning heartbeat, while the API process serves the dashboard and REST surface. Both share the same SQLite database.
   Key components:
   - Agent (Heartbeat). A long-running asyncio process that, on each interval, fetches operator acknowledgements, collects telemetry, invokes the LangGraph reasoning loop, persists the verdict, and dispatches notifications. Implemented in agent/main.py and agent/orchestrator.py.
   - FastAPI Service. Hosts the dashboard and the REST API (status, alerts, configuration, threats, runbooks, and acknowledgement endpoints) behind authentication, rate-limiting, security-header, and audit middleware. Implemented in api/main.py.
   - Reasoning Substrate. A LangGraph state machine implements the collect-analyse-decide-notify loop with two interchangeable analysis modes: a single structured provider call and a LangChain multi-tool agent.
   - LLM Client. A provider layer supporting the Gemini Developer API, Anthropic, OpenAI, and optional Ollama models through a common verdict schema.
   - Verdict-Memory. The fingerprinting and acknowledgement subsystem (agent/memory.py and the acknowledgements table) that suppresses already-triaged conditions and feeds them back into the prompt as known conditions.
   - RAG Service. A retrieval pipeline over local Markdown runbooks, local ONNX all-MiniLM-L6-v2 embeddings, and a ChromaDB vector store.
   - Threat Subsystem. A deterministic detector that scans recent logs for attack patterns and an operator-approved CrowdSec adapter.
   - SQLite Store. The persistence layer for verdicts and acknowledgements, with automatic retention pruning.

8. Reasoning workflow - "Each heartbeat follows a bounded collect-analyse-decide-notify cycle"
   Workflow: The reasoning workflow lives in agent/orchestrator.py and is started on a schedule by the asyncio heartbeat in agent/main.py. At each interval, the heartbeat loads active acknowledgements and, when Docker monitoring is enabled, may tail error logs from a monitored container. The compiled LangGraph workflow runs on a worker thread so a blocking model call cannot stall the event loop. Its collect_data node gathers telemetry, analyze requests a verdict, and decide_action may add container diagnostics for a high or critical result.
   Provider modes: Two settings control LLM analysis: USE_LANGCHAIN_AGENT selects the analysis mode, and LLM_PROVIDER selects Gemini, Anthropic, OpenAI, or Ollama. The active model name is included in the acknowledgement fingerprint. Direct mode sends the assembled prompt in one request and parses the returned JSON through the shared schema module. In multi-tool mode, the provider chat model may call the Loki, Prometheus, and HTTP-probe tools before returning a verdict, subject to an iteration limit.

   Anthropic, OpenAI-compatible endpoints, and Ollama as configurable provider options.

10. Safety and memory design - "Structured outputs and fingerprinted acknowledgements constrain recurring risk"
   Output validation: Prompt construction in agent/llm/prompts.py serialises only the telemetry sections that are available. It also instructs the model not to treat a missing optional integration as an incident. The shared parser in agent/llm/schema.py expects a JSON object and a recognised severity, then normalises the summary, root-cause, action, and signature fields. Missing text fields are replaced with empty strings and unexpected fields are ignored.
   Verdict memory: Acknowledgement behaviour spans agent/memory.py, api/store.py, the prompt assembler, and the acknowledgement endpoints; Figure 4.2 traces the flow. The condition signature is combined with the prompt version and model name to produce a SHA-256 fingerprint. An operator may acknowledge an ok or warning verdict, add a note, and choose an expiry time. Active acknowledgements are passed back in later prompts as context, although every heartbeat still calls the model. When a later ok or warning verdict has the same fingerprint, the API marks it as suppressed and the dashboard hides it by default.
